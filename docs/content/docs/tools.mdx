<AlphaNotice>

Tools are new. How a tool is declared, how it runs, and how a client reads a call will likely change before v2, so pin your version if you depend on it.

</AlphaNotice>

An MCP tool is a name, a JSON input, a JSON output, something that runs, and a rule about who may run it. You wrote all five when you wrote the route.

<Steps>

<Step>

## Mark the routes

```ts title="routes/users.ts"
export const usersRoutes = k.routes('users', {
    getUser: {
        method: 'GET',
        path: '/users/:id',
        summary: 'Fetch one user by id',
        tool: true,
        responses: {
            200: UserSchema,
        },
    },
    archiveUser: {
        method: 'POST',
        path: '/users/:id/archive',
        summary: 'Archive a user. Their data stays, and they stop appearing in lists',
        tool: true,
        responses: {
            204: z.void(),
        },
    },
});
```

`users_get_user` and `users_archive_user` are tools now. There is nothing else to write, because the route already carries everything a tool needs:

| A tool needs     | The route has it as                                  |
| ---------------- | ---------------------------------------------------- |
| a name           | its key, `users.getUser`, published `users_get_user` |
| a description    | its `summary` and `description`                      |
| an input schema  | its path parameters, query and body                  |
| an output schema | its responses                                        |
| something to run | its handler                                          |
| a rule to run by | its entry in the access control map                  |

So there is one declaration, one handler, and one place that says who may call it. A tool is a route you let a model reach.

`readOnlyHint`, `idempotentHint` and `destructiveHint` come from the method, per RFC 9110. A `GET` announces itself as safe and a `DELETE` as destructive, so no hint can contradict what the route does.

### One set of words

The model reads the route's own `summary`. Write it for a person and a model both, and if it reads too vaguely for a model it was probably too vague for the developer reading your docs.

### A tool with no API behind it

Give it a route anyway:

```ts title="routes/text.ts"
export const textRoutes = k.routes('text', {
    countWords: {
        method: 'POST',
        path: '/text/count-words',
        summary: 'Count the words in a piece of text',
        tool: true,
        body: z.object({
            text: z.string(),
        }),
        responses: {
            200: z.object({
                words: z.int(),
            }),
        },
    },
});
```

It is an ordinary route, so it reaches your client, your OpenAPI document and your tests like any other, and you can call it with curl without an MCP client anywhere in sight.

### Routes that cannot be tools

A route that [streams](/docs/streaming) has no single value to answer with, and one reading a form body has nowhere to put JSON arguments. Marking either is a compile error:

```ts
reply: {
    method: 'POST',
    path: '/assistant/reply',
    tool: true,
//  ~~~~~~~~~~
//  This route streams, so it cannot be a tool.
```

</Step>

<Step>

## What a call answers

```json
{ "status": 200, "body": { "id": "1", "name": "Ada" } }
{ "status": 404, "detail": "No user with that id" }
```

Every status the route declares travels in that envelope, so a model can tell "no such user" from a failure worth retrying. A success carries `body`, a refusal carries `detail` read from its [Problem Details](/docs/reference/problem-details-schema).

The model reads the set as a closed one. `status` is published as `enum: [200, 404, 422, 500, 503]`, and Swift and Kotlin take it as an `Int` they can switch over.

The arguments arrive split the way the route reads them, so a path parameter and a query field sharing a name cannot collide:

```json
{
    "params": { "id": "1" },
    "query": { "include": "archived" }
}
```

</Step>

<Step>

## Say who may call it

The route's entry governs the tool, because the tool runs the route:

```ts title="access-control.ts"
export const accessControl = k.accessControl(routes, {
    users: {
        '*': 'member',
        deleteUser: {
            auth: 'member',
            roles: 'owner',
        },
    },
});
```

`users_delete_user` is owner-only for a model, for the same reason `DELETE /users/:id` is owner-only for a browser. It could not work any other way: a tool with a weaker rule than the route behind it would turn your MCP endpoint into a way around the rule.

The guard runs on every tool call, against the credentials the transport carried, and its context reaches your handler under `auth` exactly as it does over HTTP.

Take the workspace from `auth`, never from the arguments. The model chooses what it sends, so a workspace id in the input is a workspace id the model picked.

</Step>

<Step>

## Put them on a stream

A streamed response names the tools it drives, and gains three events for them:

```ts title="routes/assistant.ts"
export const assistantRoutes = k.routes('assistant', {
    reply: {
        method: 'POST',
        path: '/assistant/reply',
        body: z.object({
            prompt: z.string().min(1),
        }),
        responses: {
            200: {
                stream: {
                    delta: z.object({
                        text: z.string(),
                    }),
                },
                tools: [routes.users.getUser, routes.charts.plotSignups],
            },
        },
    },
});
```

| Event         | Payload                 |
| ------------- | ----------------------- |
| `tool_call`   | `{ id, name, input }`   |
| `tool_result` | `{ id, name, output }`  |
| `tool_error`  | `{ id, name, message }` |

Each is discriminated on the tool's dotted key, so a client's `for await` narrows the payload to the tool that produced it. `id` ties a result back to its call.

The union is those two routes and nothing else, so `switch (call.name)` in your component is exhaustive over the tools you actually draw, and the Swift and Kotlin generators emit two cases rather than one per tool on the contract.

This list is not the MCP selection. `tool: true` says what a model may call over MCP; this says which tools travel on this stream, which is usually a handful even when your API publishes many. A route named here does not have to be marked `tool: true` at all, since your own loop is what calls it.

</Step>

</Steps>

## Driving the model

Every route handler receives the contract's tools under `tools`, typed against the routes you marked. This is the handler for the `assistant.reply` route from [Put them on a stream](#put-them-on-a-stream):

```ts title="server/router/assistant.ts"
import Anthropic from '@anthropic-ai/sdk';
import type { Router } from '@ts-kizuna/express';
import type { contract } from '../contract';

const anthropic = new Anthropic();

export const assistant: Router<typeof contract.routes.assistant> = {
    reply: async ({ body, tools }) => ({
        status: 200,
        body: async function* () {
            const stream = anthropic.messages.stream({
                model: 'claude-opus-5',
                max_tokens: 1024,
                messages: [{ role: 'user', content: body.prompt }],
                tools: tools.definitions.map((tool) => ({
                    name: tool.name,
                    description: tool.description,
                    input_schema: tool.inputSchema,
                })),
            });

            for await (const event of stream) {
                if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
                    yield { event: 'delta', data: { text: event.delta.text } };
                }

                if (event.type === 'content_block_stop' && event.content_block.type === 'tool_use') {
                    yield* tools.emit({
                        id: event.content_block.id,
                        name: event.content_block.name,
                        input: event.content_block.input,
                    });
                }
            }
        },
    }),
};
```

- `tools.definitions` is every tool in MCP's shape, `inputSchema` as JSON Schema. It is typed as a JSON Schema object, so it goes straight into a provider's tool list without a cast.
- `tools.emit` yields `tool_call`, runs the call, then yields either `tool_result` or `tool_error`. The call event goes out before the work starts, so a client can show it running. It takes the name the model chose, either spelling, and never throws.

When you want the outcome rather than the events, `tools.dispatch` answers it directly:

```ts
const outcome = await tools.dispatch({
    id: event.content_block.id,
    name: event.content_block.name,
    input: event.content_block.input,
});

if (outcome.ok && outcome.name === 'users.getUser') {
    console.log(outcome.output.body?.name ?? outcome.output.detail);
}
```

An unknown name, input that fails its schema, and a `throwError` from a handler all come back as `{ ok: false }` with a `message` written for the model to read and correct. `tools.keyOf` turns a published name like `users_get_user` into the dotted key when you need it on its own, and `tools.call` is the typed form for a call you already know is valid.

Reach one directly from a script or a test:

```ts
await tools.users.getUser.run({
    params: {
        id: '1',
    },
});
```

## Reading the calls

A call arrives as one event and its answer as another. `readToolCalls` folds them back into one row per call, carrying the tool's `name`, a `state` of `running`, `done` or `failed`, and the payloads narrowed to that tool.

A row reads `running` from the moment the call is made until its answer arrives, so a spinner or a pending card has something to render while the tool works.

TypeScript imports it from `@ts-kizuna/core`; the Swift and Kotlin generators emit it beside the route's `Event` type.

<Tabs items={['React', 'SwiftUI', 'Compose']}>

<Tab value="React">

`streamOptions` from [`@ts-kizuna/tanstack-query`](/docs/clients/tanstack-query) already holds the messages received so far, so there is no state to keep at all.

```tsx title="components/Chat.tsx"
import { useQuery } from '@tanstack/react-query';
import { readToolCalls } from '@ts-kizuna/core';
import { api } from '../api';

export function Chat({ prompt }: { prompt: string }) {
    const { data } = useQuery(
        api.assistant.reply.streamOptions({
            input: {
                body: {
                    prompt,
                },
            },
        })
    );

    const messages = data ?? [];

    return (
        <article>
            {readToolCalls(messages).map((call) => (
                <ToolCallView key={call.id} call={call} />
            ))}
            <p>{messages.flatMap((message) => (message.event === 'delta' ? [message.data.text] : [])).join('')}</p>
        </article>
    );
}
```

## Publishing over MCP

Every route you marked with `tool: true` is published:

```ts title="contract/index.ts"
import { mcpPlugin } from '@ts-kizuna/mcp';
import { k } from './k';
import { routes } from './routes';

export const contract = k.contract({
    routes,
    accessControl,
    plugins: {
        mcp: mcpPlugin({
            name: 'My API',
        }),
    },
});
```

The endpoint is an ordinary kizuna route, so `api.mount` serves it on any adapter, and it stays out of `contract.routes` so the client and the generators do not see it.

Every tool answers the same envelope, so a model reads one shape whichever one it called.

Whatever a route requires is enforced per call. The guard runs against the transport's credentials, and its context reaches the handler under `auth` exactly as it does over HTTP.

Every tool costs a model context on every turn, and it chooses less well from a long list. Some clients take no more than forty. Mark the routes a model has a reason to call, not every route you have.

See [MCP](/docs/mcp) for the rest of the endpoint, including OAuth.

## Two names for one tool

`users.getUser` travels on the stream. `users_get_user` is what a model calls it over MCP. `tools.keyOf` turns the second into the first.

## What kizuna leaves out

- **Models.** kizuna never calls one, holds a conversation, or runs an agent loop. The loop lives in your route handler.
- **Provider wire shapes.** There is no `toAnthropicTools` or `toOpenAITools`. `tools.definitions` hands you MCP's shape, and the `.map` to a provider is three lines.
- **Progressive tool input.** A `tool_call` is emitted once the arguments are complete, never half-parsed.
- **A second way to declare one.** A tool is a route, so there is no parallel tool tree to keep in step with your API.

## A note on standards

The declaration follows the Model Context Protocol `Tool` object, and its schemas follow JSON Schema 2020-12. The three event names are kizuna's own, since no standard covers streamed tool calls. See [standards](/docs/standards).
