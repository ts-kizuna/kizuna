<BetaNotice>

Tools are new and still settling. `k.tools`, the `tools` field on a streamed response, and the event names may change before v2, so pin your version if you depend on them.

</BetaNotice>

A tool is usually written three times: a JSON Schema for the model, a typed event for the client, and a function that runs it. Declare it once and all three follow.

<Steps>

<Step>

## Declare the tools

The fields mirror the [Model Context Protocol](https://modelcontextprotocol.io/specification/latest/server/tools) `Tool` object.

```ts title="contract/tools.ts"
import { z } from 'zod';
import { k } from './k';

export const tools = k.tools({
    weather: {
        getForecast: {
            title: 'Weather forecast',
            description: 'Look up tomorrow forecast for one city',
            input: z.object({
                city: z.string().min(1),
                unit: z.enum(['celsius', 'fahrenheit']).default('celsius'),
            }),
            output: z.object({
                temperature: z.number(),
                unit: z.enum(['celsius', 'fahrenheit']),
                summary: z.string(),
            }),
        },
    },
});
```

| Field         | Meaning                                                              |
| ------------- | -------------------------------------------------------------------- |
| `description` | What the model reads when it decides whether to call. Required       |
| `input`       | Schema for the arguments the model sends                             |
| `output`      | Schema for what the tool answers                                     |
| `title`       | A human-readable name for display                                    |
| `annotations` | `readOnlyHint`, `idempotentHint`, `destructiveHint`, `openWorldHint` |

Tools nest like routes, and a tool is addressed by its dotted key. Install them beside `routes`:

```ts title="contract/index.ts"
export const contract = k.contract({
    routes,
    tools,
    auth,
});
```

A tool declares no path and no method, so nothing that walks `contract.routes` sees one.

</Step>

<Step>

## Put them on a stream

Naming `tools` on a streamed response adds three events:

```ts title="contract/assistant.ts"
responses: {
    200: {
        stream: {
            delta: z.object({
                text: z.string(),
            }),
        },
        tools,
    },
},
```

| Event         | Payload                 |
| ------------- | ----------------------- |
| `tool_call`   | `{ id, name, input }`   |
| `tool_result` | `{ id, name, output }`  |
| `tool_error`  | `{ id, name, message }` |

`id` ties a result back to its call.

</Step>

<Step>

## Write the handlers

A handler receives the validated `input`, `throwError`, and the identity its tool requires. Anything else it imports, the way a route handler does.

```ts title="server/tools.ts"
import { forecastFor } from '../weather';
import { server } from './server';

export const toolHandlers = server.tools({
    weather: {
        getForecast: ({ input, throwError }) => {
            if (input.city.trim() === '') {
                throwError('Name a city to look the forecast up for.');
            }
            return forecastFor(input.city, input.unit);
        },
    },
});
```

`throwError` takes a message rather than a `{ status, body }` envelope, since a tool has no HTTP status. It reaches the client as a `tool_error`, and a model over MCP reads it as an execution error it can retry.

</Step>

<Step>

## Say who may call it

A tool that changes something, or reads someone's data, needs to know who is asking. Give it an [identity](/docs/authentication), narrowed by whatever the caller has to be:

```ts title="tools.ts"
export const tools = k.tools({
    purgeCache: {
        auth: {
            member: {
                role: 'owner',
            },
        },
        description: 'Drop every cached report. There is no undo.',
        output: z.object({
            dropped: z.int(),
        }),
        annotations: {
            destructiveHint: true,
        },
    },
});
```

```ts title="server/tools.ts"
purgeCache: ({ auth }) => dropReportsFor(auth.member.workspaceId),
```

`auth.member` is that identity's context, typed, with `role` narrowed to `'owner'`. A caller holding `admin` is refused before the handler runs, and so is a caller holding nothing.

`auth` takes the same values a route's entry in the auth map takes: an identity name, several, or one narrowed by an access field.

The workspace is not an `input` field. The model chooses `input`, so a selector declared there is a selector the model picks.

A tool naming a route with `fromRoute` says nothing about who may call it. The route already does.

Outside a request nobody has been verified, so bind a caller yourself:

```ts
const asOwner = tools.as({
    member: {
        workspaceId: 'w_1',
        role: 'owner',
    },
});

await asOwner.purgeCache.run();
```

</Step>

<Step>

## Register them on the api

```ts title="server/api.ts"
export const api = server.api({
    router,
    tools: toolHandlers,
});
```

</Step>

## A route your model can call

A route already has an input schema, an output schema, a handler, and an identity it requires, which is everything a tool is. Name it:

```ts title="tools.ts"
export const tools = k.tools(({ fromRoute }) => ({
    users: {
        find: fromRoute(routes.users.getUser),
        list: fromRoute(routes.users.listUsers),
    },
}));
```

`k.tools` hands the builder a `fromRoute`. `k.tools.fromRoute` is the same function, for when you want it once.

The tool takes the route's path parameters, query and body as its arguments, answers with the route's own responses, describes itself from the route's summary, and runs the route's handler. Its `readOnlyHint` and `destructiveHint` come from what RFC 9110 says about the method, so a `GET` is marked safe and a `DELETE` destructive.

The key is yours. `find` reads better to a model than `getUser`, and the route keeps its own name.

### What it answers with

```json
{ "status": 200, "body": { "id": "1", "name": "Ada" } }
```

A `404` arrives the same way, with `status: 404`, which is what lets a model tell "no such user" apart from a failure worth retrying. The envelope carries every success status a route declares, so one answering both `200` and `201` still has one result type.

### Who may call it

The route's own `security` and `accessGate` decide, so authorization stays in [`k.auth`](/docs/authentication) and governs both surfaces from one declaration. A caller has to carry the identity the route requires.

### Routes that cannot be tools

A route whose response [streams](/docs/streaming) has no single value to answer with, and one that reads a form body has nowhere to put JSON arguments. Naming either is a compile error where you named it:

```ts
fromRoute(routes.assistant.reply);
//        ~~~~~~~~~~~~~~~~~~~~~
// This route streams, so it cannot be a tool.
```

### Saying it differently for a model

A route's summary is written for a developer reading your docs. A model reads the description to decide whether to call the tool at all, so give it its own words when the two differ:

```ts title="tools.ts"
pause: fromRoute(routes.meta.pauseAd, {
    description: 'Pause a running ad. The spend stops within a minute.',
}),
```

`title` and `annotations` take an override the same way.

## Driving the model

Every handler receives the contract's tools under `tools`:

```ts title="server/router/assistant.ts"
import Anthropic from '@anthropic-ai/sdk';

const anthropic = new Anthropic();

reply: ({ body, tools }) => ({
    status: 200,
    body: async function* () {
        const stream = anthropic.messages.stream({
            model: 'claude-opus-5',
            max_tokens: 1024,
            messages: [{ role: 'user', content: body.prompt }],
            tools: tools.definitions.map((tool) => ({
                name: tool.name,
                description: tool.description,
                input_schema: tool.inputSchema,
            })),
        });

        for await (const event of stream) {
            if (event.type === 'content_block_delta' && event.delta.type === 'text_delta') {
                yield { event: 'delta', data: { text: event.delta.text } };
            }

            if (event.type === 'content_block_stop' && event.content_block.type === 'tool_use') {
                yield* tools.emit({
                    id: event.content_block.id,
                    name: event.content_block.name,
                    input: event.content_block.input,
                });
            }
        }
    },
}),
```

- `tools.definitions` is every tool in MCP's shape, `inputSchema` as JSON Schema. It is typed as a JSON Schema object, so it goes straight into a provider's tool list without a cast.
- `tools.emit` runs a call and yields `tool_call`, then either `tool_result` or `tool_error`, in the order the stream wants them. It takes the name the model chose, either spelling, and never throws.

When you want the outcome rather than the events, `tools.dispatch` answers it directly:

```ts
const outcome = await tools.dispatch({
    id: event.content_block.id,
    name: event.content_block.name,
    input: event.content_block.input,
});

if (outcome.ok && outcome.name === 'weather.getForecast') {
    console.log(outcome.output.temperature);
}
```

An unknown name, input that fails its schema, and a `throwError` from a handler all come back as `{ ok: false }` with a `message` written for the model to read and correct. `tools.keyOf` turns a published name like `weather_get_forecast` into the dotted key when you need it on its own, and `tools.call` is the typed form for a call you already know is valid.

Reach one directly from a script or a test:

```ts
await tools.weather.getForecast.run({
    city: 'Oslo',
});
```

## Reading the calls

A call arrives as one event and its answer as another. `readToolCalls` folds them back into one row per call, carrying the tool's `name`, a `state` of `running`, `done` or `failed`, and the payloads narrowed to that tool.

TypeScript imports it from `@ts-kizuna/core`; the Swift and Kotlin generators emit it beside the route's `Event` type.

<Tab value="React">

`streamOptions` from [`@ts-kizuna/tanstack-query`](/docs/clients/tanstack-query) already holds the messages received so far, so there is no state to keep at all.

```tsx title="components/Chat.tsx"
import { useQuery } from '@tanstack/react-query';
import { readToolCalls } from '@ts-kizuna/core';
import { api } from '../api';

export function Chat({ prompt }: { prompt: string }) {
    const { data } = useQuery(
        api.assistant.reply.streamOptions({
            input: {
                body: {
                    prompt,
                },
            },
        })
    );

    const messages = data ?? [];

    return (
        <article>
            {readToolCalls(messages).map((call) => (
                <ToolCallView key={call.id} call={call} />
            ))}
            <p>{messages.flatMap((message) => (message.event === 'delta' ? [message.data.text] : [])).join('')}</p>
        </article>
    );
}
```

## Publishing over MCP

A declared tool already has a name, a description, an input schema, an output schema and a handler, which is what an MCP tool is. Every one is published, because a tool is a tool:

```ts title="contract/index.ts"
import { mcpPlugin } from '@ts-kizuna/mcp';
import { k } from './k';
import { routes } from './routes';
import { tools } from './tools';

export const contract = k.contract({
    routes,
    tools,
    plugins: ({ routes, tools }) => ({
        mcp: mcpPlugin({
            routes,
            tools,
        }),
    }),
});
```

Every tool in the tree is published, both the ones you declared and the routes you named with `fromRoute`.

A published tool answers with its own output, where a route published as a tool answers with the `{ status, body }` envelope its HTTP shape implies. Give the group an identity and its guard runs on every call, and the context it resolves reaches the handler under `auth`:

```ts
export const auth = k.auth(routes, tools, {
    getForecast: 'user',
});
```

See [MCP](/docs/mcp) for the rest of the endpoint, including OAuth.

## How it works underneath

Nothing here is a new transport. Every piece reduces to something kizuna already had.

**The events are folded into the stream at `k.routes` time.** `tools` on a response is authoring sugar. Before a route is validated, `expandStreamTools` turns each tool into three Zod schemas and merges them into the response's `stream` record, then deletes the `tools` field. From that point on the response is an ordinary named-event stream, which is why the four adapters, the OpenAPI generator, the fetch client, and the Swift and Kotlin generators needed no changes to carry tools.

**Each event is a discriminated union on the tool's dotted key.** `tool_call` is `z.discriminatedUnion('name', [...])` with one arm per tool, each carrying that tool's own `input` schema. The type-level side walks the tool tree to the same dotted keys, so `message.data.input` narrows in TypeScript, the Swift generator emits an `enum` with one case per tool, and the Kotlin generator emits a `sealed interface`. The `id` and `name` accessors you read without switching are generated from the fields every arm shares.

**The dotted key is the discriminator, not the published name.** `weather.getForecast` on the wire, `weather_get_forecast` over MCP. Deriving the snake-case name at the type level would need a string algorithm that has to agree exactly with the runtime one, and disagreeing silently would be worse than the one `tools.keyOf` call it costs you.

**Execution is one runner.** `createToolRunner` pairs the contract's tools with their handlers and hands the result to every route handler as `tools`, the same way `jobs` is threaded. `tools.call`, `tools.<key>.run` and the MCP endpoint all go through it, so input validation, the handler, and output validation happen in one place whoever asked.

**Publishing is a projection.** `resolveTools` resolves the MCP name and the declaration behind it. `tools.definitions` converts its schemas to JSON Schema for a model; the MCP plugin hands the Zod schemas to the MCP SDK, which converts them itself. Both read the same derivation, so a tool is named and described in one place.

## What kizuna leaves out

- **Models.** kizuna never calls one, holds a conversation, or runs an agent loop. It validates input, runs a handler, validates output. The loop lives in your route handler, the way a job's transport lives outside kizuna.
- **Provider wire shapes.** There is no `toAnthropicTools` or `toOpenAITools`, because those track a vendor changelog. `tools.definitions` hands you MCP's shape and the `.map` to a provider is a few lines you can read.
- **Progressive tool input.** A model streams a tool's arguments as partial JSON, which has no schema until it is whole. A half-parsed `{ city: "Os" }` would type-check as a finished value while being wrong, so kizuna emits `tool_call` once the arguments are complete.

## A note on standards

The declaration follows the Model Context Protocol `Tool` object, and its schemas follow JSON Schema 2020-12. The three event names are kizuna's own, since no standard covers streamed tool calls. See [standards](/docs/standards).
