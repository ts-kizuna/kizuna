`@ts-kizuna/openapi` generates an [OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0) document from your contract.

<InstallTabs packageName="@ts-kizuna/openapi" />

## Install it

`openApiPlugin` serves the document and an API reference UI for it, on any adapter.

<Steps>

<Step>

## Declare the plugin

```ts title="k.ts"
import { Kizuna } from '@ts-kizuna/contract';
import { openApiPlugin } from '@ts-kizuna/openapi';

export const k = new Kizuna({
    tags,
    plugins: {
        openApi: openApiPlugin({
            info: {
                title: 'My API',
                version: '1.0.0',
            },
            docsPath: '/docs',
        }),
    },
});
```

</Step>

<Step>

## Register its server half

`server.api` is where the generator itself lives:

```ts title="api.ts"
import { openApiPluginServer } from '@ts-kizuna/openapi/server';

export const api = server.api({
    router,
    plugins: {
        openApi: openApiPluginServer(),
    },
});
```

</Step>

</Steps>

Each prop serves one route, and serves nothing until you give it a path:

| Prop       | Serves                                  | Path            |
| ---------- | --------------------------------------- | --------------- |
| `docsPath` | the API reference UI, Scalar by default | anything        |
| `jsonPath` | the document                            | ends in `.json` |
| `yamlPath` | the document as YAML                    | ends in `.yaml` |

```ts
openApiPlugin({
    info,
    docsPath: '/docs',
    jsonPath: '/openapi.json',
});
```

The UI embeds the document, so `docsPath` alone is enough to browse the API. All three are [plugin routes](/docs/plugins#plugin-routes), so they stay out of your fetch client and out of the document itself.

The routes are public. Gate them with your framework's own middleware if that is not what you want.

### Writing it to disk

```ts title="generate-openapi.ts"
import { writeFileSync } from 'fs';
import { generateOpenApi } from '@ts-kizuna/openapi/server';
import { contract } from '../src/contract';

const spec = generateOpenApi(contract);

writeFileSync('openapi.yaml', spec('yaml'));
```

```sh title="Terminal"
tsx scripts/generate-openapi.ts
```

### Serving it yourself

[`generateOpenApi`](#generateopenapi) renders the document directly:

```ts title="src/index.ts"
const spec = generateOpenApi(contract);

app.get('/openapi.yaml', (_req, res) => {
    res.type('text/yaml; charset=utf-8').send(spec('yaml'));
});
```

Leave `yamlPath` unset when you do, or two handlers claim the path and whichever registered first wins. Kizuna sees collisions between the contract and a plugin, but a route you register on the app yourself is invisible to it.

Mixing is the useful case: set `jsonPath` and leave `docsPath` unset, and the plugin serves the document while you render your own UI.

### Swagger instead of Scalar

```ts
openApiPlugin({
    info,
    provider: 'swagger',
});
```

Point `cdnUrl` at a self-hosted copy for air-gapped deployments or a strict CSP.

## `generateOpenApi`

`generateOpenApi` returns a renderer. Call it with `'json'` for the document object or `'yaml'` for a YAML string. Everything it needs, `info` included, comes off the contract, declared once on [`openApiPlugin`](#declare-the-plugin) in `k.ts`.

```ts title="generate-openapi.ts"
import { generateOpenApi } from '@ts-kizuna/openapi/server';
import { contract } from '@/contract';

const spec = generateOpenApi(contract);

spec('json'); // OpenApiDocument object
spec('yaml'); // YAML string
```

## Deprecation

Routes and fields marked `/** @deprecated */` get `deprecated: true` in the generated spec, with no extra options here. `generateOpenApi(contract)` reads them straight off the contract, once you've added the one-time build step. See [Deprecations](/docs/deprecations) for setup.

## Options

They go on `openApiPlugin` in `k.ts`, and `generateOpenApi` reads them from there.

```ts title="k.ts"
openApiPlugin({
    info: {
        title: 'My API',
        version: '1.0.0',
        description: 'Optional description',
    },
    servers: [
        {
            url: 'https://api.example.com',
            description: 'Production',
        },
        {
            url: 'http://localhost:3000',
            description: 'Development',
        },
    ],
    setOperationId: true,
});
```

| Option            | Default  | Description                                                                             |
| ----------------- | -------- | --------------------------------------------------------------------------------------- |
| `info`            | required | OpenAPI `info` object                                                                   |
| `servers`         | none     | Server URLs                                                                             |
| `setOperationId`  | `false`  | Set `operationId` from the route key. Use `'concatenated-path'` to include parent keys. |
| `operationMapper` | none     | Callback to transform each operation before it is added to the spec                     |

## Security

Security comes from the contract. The [identities](/docs/authentication) you register on `new Kizuna()` are emitted as `components.securitySchemes`, and the contract's auth map becomes each operation's `security`, with oauth2 scopes included. There are no generator options for it, so the spec cannot disagree with what the server enforces.

```ts title="identities.ts"
export const user = Kizuna.identity.bearer({
    context: z.object({
        userId: z.string(),
    }),
});
```

```yaml title="openapi.yaml"
# generated
components:
    securitySchemes:
        user:
            type: http
            scheme: bearer
paths:
    /workspace:
        get:
            security:
                - user: []
```

Routes marked `false` in the auth map get no `security` entry. A [`custom`](/docs/reference/kizuna-identity#custom-identities) identity also emits no `security`, since OpenAPI can't describe its credential, but its routes carry an `x-kizuna-guarded` extension so they stay distinguishable from public ones.

## Validation errors

Routes with a `body` or `query` schema automatically include a `400` validation error response, matching what kizuna returns when request data fails validation. A route that declares its own `400` keeps it; nothing is added.

## Breaking changes

Use [oasdiff](https://github.com/oasdiff/oasdiff) to compare your generated spec against a previous version and catch breaking changes before they ship. See the [Breaking Changes](/docs/breaking-changes) guide for setup and CI integration.

[Scheduled jobs](/docs/jobs) live under `jobs` on the contract, not `routes`, so they are not in the document.
