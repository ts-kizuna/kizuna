<BetaNotice>

Deprecations are new and still settling. How deprecations reach each generated client may change before v2, so pin your version if you depend on them.

</BetaNotice>

A deprecation is declared once, on the contract, and every output picks it up from there: `deprecated: true` in the OpenAPI spec, `@available(*, deprecated)` in the Swift client, `@Deprecated` in the Kotlin client, and a strikethrough in editors. There is no build step and nothing to deploy.

## Routes

Set `deprecated` on the route, either `true` or a migration message:

```ts title="contract/index.ts"
export const usersRoutes = k.routes('users', {
    deleteUser: {
        method: 'DELETE',
        path: '/users/:id',
        deprecated: 'use archiveUser instead',
        responses: {
            200: z.object({
                ok: z.boolean(),
            }),
        },
    },
});
```

## Fields

Fields declare it in their Zod metadata, with the same `true | string` shape:

```ts
const UserSchema = z.object({
    id: z.string(),
    email: z.string().meta({
        deprecated: 'use email_address instead',
    }),
    email_address: z.string(),
});
```

Zod declares `deprecated` as a boolean; `@ts-kizuna/core` widens it to accept the message string, so this type-checks in any file that is part of a project using kizuna.

## What each output emits

OpenAPI marks the operation and the field's schema with `deprecated: true` (the spec has no message field). Swift emits `@available(*, deprecated, message: "use email_address instead")` and Kotlin `@Deprecated("use email_address instead")`, so the message reaches autocomplete and compiler warnings in both mobile clients.

## Editors

TypeScript does not read Zod metadata, so strikethrough in editors comes from `@ts-kizuna/typescript-plugin`, a TypeScript language service plugin. It flags usages of deprecated routes and fields, everywhere the contract's types flow: `client.deleteUser(...)`, a response's `user.email`, completions, and hover, which shows the migration message.

In VS Code and its forks (Cursor, Windsurf), install the **ts-kizuna** editor extension and you are done.

In any other editor that uses the TypeScript server (Zed, Neovim, JetBrains), add the plugin as a dev dependency and declare it in `tsconfig.json`:

```json title="tsconfig.json"
{
    "compilerOptions": {
        "plugins": [
            {
                "name": "@ts-kizuna/typescript-plugin"
            }
        ]
    }
}
```

The same tsconfig entry works in VS Code with the workspace TypeScript version selected, if you prefer per-project configuration over the extension.

Editor strikethrough follows the contract's source, so it applies within the repository that defines the contract. A contract consumed as a published package still carries its deprecations into every generated output.

## Published packages

When you publish your contract or schemas as a package, the JSDoc you wrote on Zod fields is lost: declaration emit serializes the inferred `z.ZodObject<{...}>`, whose properties carry no comments. Run `kizuna dts` after your build to re-inject each field's JSDoc block, descriptions and `@example`, into the emitted `.d.ts`:

```json title="package.json"
{
    "scripts": {
        "build": "tsdown src/index.ts --dts && kizuna dts src/index.ts --out dist"
    }
}
```

The `kizuna` CLI ships in `@ts-kizuna/cli`, a build-time dev dependency:
