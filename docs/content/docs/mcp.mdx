<BetaNotice>

MCP support is new and still settling. The plugin options and the generated tool surface may change before v2, so pin your version if you depend on them.

</BetaNotice>

`@ts-kizuna/mcp` adds an [MCP (Model Context Protocol)](https://modelcontextprotocol.io) endpoint to your API. Each route becomes an MCP tool that AI assistants can discover and call.

<InstallTabs packageName="@ts-kizuna/mcp" />

<Steps>

<Step>

## Declare the plugin

MCP is a [plugin](/docs/plugins), declared on `k.contract` and served by `api.mount`:

```ts title="contract.ts"
import { mcpPlugin } from '@ts-kizuna/mcp';
import { k } from './k';
import { routes } from './routes';
import { auth } from './auth';

export const contract = k.contract({
    routes,
    auth,
    plugins: {
        mcp: mcpPlugin({
            name: 'My API',
        }),
    },
});
```

</Step>

<Step>

## Register its server half

`server.api` is where the MCP SDK and the transport live:

```ts title="api.ts"
import { mcpPluginServer } from '@ts-kizuna/mcp/server';

export const api = server.api({
    router,
    plugins: {
        mcp: mcpPluginServer(),
    },
});
```

</Step>

</Steps>

The endpoint answers at `/mcp` by default. On Next.js it is served by the catch-all route file that already serves your contract, so with `basePath: '/api'` it lands at `/api/mcp`.

## Choosing which routes become tools

Name the routes a model may call with [`fromRoute`](/docs/tools):

```ts title="tools.ts"
export const tools = k.tools(({ fromRoute }) => ({
    users: {
        find: fromRoute(routes.users.getUser),
        list: fromRoute(routes.users.listUsers),
    },
}));
```

A route is a tool when it is written here. Everything about it comes from the route: its arguments, its result, its description, its annotations, and the identity it requires.

Give the model its own words when the route's summary is written for a developer reading your docs:

```ts title="tools.ts"
pause: fromRoute(routes.meta.pauseAd, {
    description: 'Pause a running ad. The spend stops within a minute.',
}),
```

`onlyReadOnly` keeps only the tools that cannot change data, so nothing an assistant calls writes anything:

```ts title="contract.ts"
mcp: mcpPlugin({
    name: 'My API',
    onlyReadOnly: true,
}),
```

A route reads its safety from its method, per RFC 9110, so a `GET` declares `readOnlyHint` and a `DELETE` declares `destructiveHint`.

Routes whose `contentType` is `multipart/form-data` or `application/x-www-form-urlencoded` cannot be tools, because MCP tool input is JSON. Routes whose response [streams](/docs/streaming) cannot either, because a tool result is one value. Naming one is a compile error where you named it.

### What to leave out

Every tool costs the model context on every turn, whether it calls it or not, and it chooses less well from a long list. Some clients take no more than forty.

- **Ones an assistant cannot use.** File uploads, CSV exports, anything returning bytes.
- **Ones that exist for your own infrastructure.** Health checks, readiness probes, webhook receivers.
- **Ones you do not want reached by inference.** Deleting a workspace is a person's decision, guard or no guard.

## Tools with no route behind them

A tool declared with [`k.tools`](/docs/tools) has a name, a description, an input schema, an output schema and a handler, which is what an MCP tool is. Both kinds sit in the same tree and publish the same way:

```ts title="tools.ts"
export const tools = k.tools(({ fromRoute }) => ({
    users: {
        find: fromRoute(routes.users.getUser),
    },
    countWords: {
        description: 'Count the words in a piece of text',
        input: z.object({
            text: z.string(),
        }),
        output: z.object({
            words: z.int(),
        }),
    },
});
```

Two differences from a route published as a tool:

- It answers with its own `output`, where a route answers with the `{ status, body }` envelope its HTTP shape implies.
- `onlyReadOnly` keeps it only when it declares `annotations.readOnlyHint`, since a tool has no method to read safety from.

Give the group an identity and its guard runs on every call, the way a route's `security` does. The context it resolves reaches the handler under `auth`, keyed by the identity's name, exactly as a route handler receives it:

```ts
export const tools = k.tools('user', {
    weather: {
        getForecast: { ... },
    },
});
```

## What each tool looks like

| Part            | Where it comes from                                                                 |
| --------------- | ----------------------------------------------------------------------------------- |
| **Name**        | The route key in snake_case, so `users.getUser` becomes `users_get_user`            |
| **Title**       | The route's `summary`                                                               |
| **Description** | The route's `summary` and `description`, its method and path, and what it requires  |
| **Input**       | `{ params, query, body }`, holding only the keys the route declares                 |
| **Output**      | The success response's schema, so an assistant knows the shape before it calls      |
| **Annotations** | The method's HTTP semantics, per [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) |

The [specification](https://modelcontextprotocol.io/specification/latest/server/tools) allows the dot, but Claude Code and VS Code rewrite it before the name reaches the model, so publishing the rewritten form is what keeps your docs and the model's tool name the same. Names are capped at 56 characters, which leaves room for the prefix a client adds when it aggregates several servers. Cursor rejects anything longer than 60. A key over the budget throws at startup, as do two keys that converge on one name.

The annotations tell a client how careful to be with a tool before calling it:

| Method                   | Hints set                           |
| ------------------------ | ----------------------------------- |
| `GET`, `HEAD`, `OPTIONS` | `readOnlyHint`, `idempotentHint`    |
| `PUT`                    | `idempotentHint`                    |
| `DELETE`                 | `idempotentHint`, `destructiveHint` |
| `POST`, `PATCH`          | none                                |

An absent hint is not a neutral one. MCP defaults `destructiveHint` and `openWorldHint` to true and `readOnlyHint` to false, so a client already treats `POST` and `PATCH` as destructive calls against an open world. The hints worth setting are the ones that make a tool safer than that, which is why `GET` gets `readOnlyHint` and `POST` gets nothing.

Handlers receive the same framework context they do over HTTP, passed through from the transport request, so one reading `req` or `c` keeps working as a tool.

## What the model reads

### From each route

A route's `summary` and `description` are the tool's title and description:

```ts title="routes/users.ts"
searchUsers: {
    method: 'GET',
    path: '/users/search',
    summary: 'Search users by name or email',
    description: 'Matches a name or email substring, case insensitive. Returns at most 25 users, best match first.',
    query: z.object({
        term: z.string(),
    }),
    responses: {
        200: z.array(UserSchema),
    },
},
```

The tool that reaches the model carries both, followed by the request line and the identities the route requires:

```text
Search users by name or email
Matches a name or email substring, case insensitive. Returns at most 25 users, best match first.

HTTP: GET /users/search
Requires: user
```

These are the same two fields that become `operation.summary` and `operation.description` in your OpenAPI document, and the doc comment on your generated Swift and Kotlin methods, which uses the summary and falls back to the description. Write them once for every reader. OpenAPI wants a short summary and a verbose account of the behaviour, which is what a model wants too, so naming the limit, the ordering, and the matching rule costs nothing and serves all three:

```ts title="routes/notifications.ts"
listEvents: {
    method: 'GET',
    path: '/events',
    summary: 'List session events, newest first',
    description: 'Returns one page of events, 50 per page. Timestamps are RFC 3339 in UTC.',
    query: z.object({
        page: z.int().min(1).default(1),
    }),
    responses: {
        200: z.array(EventRecord),
    },
},
```

### From the whole server

`instructions` is a single string clients put in front of the model before it picks any tool. kizuna builds one from your [tags](/docs/reference/kizuna-tags), so the groups in your contract arrive with their titles and descriptions, and your own text is appended to it:

```ts title="k.ts"
mcp: mcpPlugin({
    name: 'My API',
    instructions: 'Resolve a workspace before creating members. Every timestamp is UTC.',
}),
```

Use it for what belongs to no single route: the order operations happen in, the conventions every route shares, which tool to reach for when two look alike. That last one is worth keeping out of a route's own `description`, where it would read oddly in your API reference.

## Authentication

Secured tools authenticate via the headers of the MCP transport request. The endpoint runs the [guards](/docs/authentication) registered on `server.api`, exactly like the HTTP pipeline: the credential is extracted from the headers, the guard verifies it, access gates apply, and the handler receives its typed identity context.

A route's identities appear in its tool description, along with the scopes and access constraints that go with them, so an assistant can tell it will be refused without spending a call to find out:

```text
Delete the workspace

HTTP: DELETE /workspace
Requires: member (role: owner)
```

Configure the MCP client to send the credential as a header on the connection. For example, with Claude Code:

```sh title="Terminal"
claude mcp add --transport http my-api http://localhost:3000/mcp --header "Authorization: Bearer <token>"
```

For an `apiKey` identity, send the header the identity names (e.g. `x-workspace-token`) instead.

When a guard denies the call, or an access gate fails, the tool call returns an error result (`isError: true`) carrying the status and detail, so the assistant sees exactly why it was refused:

```json
{
    "status": 401,
    "body": {
        "detail": "Unauthorized"
    }
}
```

Public routes (`false` in the auth map) run without guards, credentials or not.

## OAuth

Point `oauth` at your [oauth2 identity](/docs/authentication#oauth) and the endpoint serves the discovery and challenges the MCP authorization specification asks of an OAuth 2.1 resource server. MCP clients log in through your authorization server (better-auth, Auth0, Keycloak) on their own.

```ts title="contract.ts"
plugins: {
    mcp: mcpPlugin({
        oauth: {
            resource: 'https://api.example.com/mcp',
            scheme: 'user',
        },
    }),
},
```

`resource` is the canonical URI of the endpoint as clients reach it, and the audience your guard checks tokens against. `scheme` names the identity whose guard verifies the token on every request. The identity's `issuer` and flow scopes become the RFC 9728 metadata document, served at `/.well-known/oauth-protected-resource/mcp`.

With `oauth` configured, denials from that identity move to the HTTP level, where the specification puts them:

- No token, or a bad one, answers `401` with `WWW-Authenticate: Bearer resource_metadata="..."`.
- A `deny(403)` from the guard on a tool call answers `403` with `error="insufficient_scope"` and the scopes the route declares in the auth map.
- An access-gate failure answers a plain `403`.

The guard runs once per request, its context reaches handlers under `auth.<scheme>` as always, and every other identity keeps the in-band tool errors above.

## Options

All of them go on `mcpPlugin`. `mcpPluginServer()` takes nothing.

| Option         | Default              | Description                                                          |
| -------------- | -------------------- | -------------------------------------------------------------------- |
| `path`         | `'/mcp'`             | Path the endpoint is served from                                     |
| `name`         | `'MCP Server'`       | Human-readable name shown to AI assistants                           |
| `version`      | `'1.0.0'`            | Semantic version string                                              |
| `instructions` | built from your tags | Appended to the generated overview                                   |
| `routes`       | none                 | The contract's routes                                                |
| `tools`        | none                 | The contract's tools                                                 |
| `onlyReadOnly` | `false`              | Publish only the tools that cannot change data                       |
| `oauth`        | off                  | Serve the endpoint as an OAuth 2.1 resource server ([OAuth](#oauth)) |

## Tool input structure

Tool inputs use structured keys that mirror the kizuna handler args:

```json
{
    "params": { "id": "42" },
    "query": { "page": 1, "limit": 25 },
    "body": { "name": "Alice", "email": "alice@example.com" }
}
```

Only the keys the route declares are present.

## Tool responses

Every tool returns a JSON text block with the HTTP status and parsed response body:

```json
{
    "status": 200,
    "body": {
        "id": "42",
        "name": "Alice"
    }
}
```

The same body is attached as `structuredContent`, matching the output schema the tool advertised, so a client can read the response as data rather than parsing the text.

Responses with status >= 400 set `isError: true` on the MCP result so the AI knows the call failed.

## Standalone server

If you want to drive the transport yourself, for stdio or SSE, [`createMcpServer`](/docs/reference/create-mcp-server) returns a raw `McpServer`:

```ts title="src/index.ts"
import { createMcpServer } from '@ts-kizuna/mcp';
import { StdioServerTransport } from '@modelcontextprotocol/sdk/server/stdio.js';
import { api } from './api';

const server = createMcpServer(api, {
    name: 'My API',
    version: '1.0.0',
});

await server.connect(new StdioServerTransport());
```
