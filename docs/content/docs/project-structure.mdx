ts-kizuna has no opinion about your file layout. A single file works. The one thing it needs is a contract that every side of your app can import.

The layout below is the one we use ourselves. It goes from a handful of routes to a few hundred without anything moving. Two shapes cover almost everything:

<Cards>
    <Card title="Monorepo" href="#monorepo">
        The API and its consumers are separate apps, and the contract is a package they both import.

## Monorepo

```
my-repo/
├── packages/
│   └── contract/
│       └── src/
│           ├── k.ts            # new Kizuna(), exports k
│           ├── tags.ts         # Kizuna.tags
│           ├── identities.ts   # Kizuna.identity builders
│           ├── routes/
│           │   ├── users.ts    # k.routes('users', { ... })
│           │   ├── events.ts
│           │   ├── health.ts
│           │   └── index.ts    # re-exports the groups
│           ├── auth.ts         # k.auth, who may call what
│           ├── jobs.ts         # k.jobs
│           └── contract.ts     # k.contract, the object everything reads
├── apps/
│   ├── api/
│   │   └── src/
│   │       ├── server/
│   │       │   ├── server.ts   # new KizunaServer(contract)
│   │       │   ├── guards.ts   # server.guard per identity
│   │       │   ├── router/
│   │       │   │   ├── users.ts    # Router<typeof contract.routes.users>
│   │       │   │   ├── events.ts
│   │       │   │   ├── health.ts
│   │       │   │   └── index.ts    # server.router, composes the groups
│   │       │   ├── jobs.ts     # server.jobs
│   │       │   └── api.ts      # server.api, what you mount
│   │       └── index.ts        # api.mount(app)
│   └── website/
│       └── src/lib/api-client.ts   # new KizunaClient(contract)
└── package.json
```

## Why the contract is its own package

Your server, your website, and anything else that talks to the API all import the contract. Inside the API app, every consumer has to reach into that app to get it.

Its own package also keeps it browser-safe. The contract is plain data, and a separate package cannot accidentally pick up a database driver or a Node built-in.

It also decides what the contract is allowed to hold. Everything it imports travels with it to every client, so it stays route shapes only. Server config, API keys, and `process.env` reads live in the API app, next to the handlers that read them.

Publishing it is then a small step. Teams with API consumers outside the repo push the contract to npm, public or private, so anyone integrating installs one package and gets the routes, the types, and a client that knows both.

## Splitting the pieces

The split matters more as the API grows:

- **`k.ts`** constructs the surface once. Everything else imports `k` from here.
- **`routes/`** holds one file per group, each calling `k.routes`, with an `index.ts` re-exporting them so `contract.ts` has one import to make. See [organizing the contract](/docs/building/contract#splitting-routes-across-files).
- **`router/`** mirrors it exactly. One file per group, each typed with the [`Router`](/docs/building/router#routehandler-and-router-types) type so inputs and responses stay inferred, and `index.ts` composes them with `server.router`.
- **`auth.ts`** declares who may call what, once, against the whole route tree, so one file answers the question. See [authentication](/docs/authentication).
- **`api.ts`** is where guards, jobs, plugins, and the router come together.

## Single app

With Next.js the API and the website are the same app, so the contract can be a folder instead of a package:

```
my-repo/
└── src/
    ├── contract/
    │   ├── k.ts            # new Kizuna(), exports k
    │   ├── tags.ts         # Kizuna.tags
    │   ├── identities.ts   # Kizuna.identity builders
    │   ├── routes/
    │   │   ├── users.ts    # k.routes('users', { ... })
    │   │   ├── events.ts
    │   │   ├── health.ts
    │   │   └── index.ts    # re-exports the groups
    │   ├── auth.ts         # k.auth, who may call what
    │   ├── jobs.ts         # k.jobs
    │   └── index.ts        # k.contract, the object everything reads
    ├── server/
    │   ├── server.ts       # new KizunaServer(contract)
    │   ├── guards.ts       # server.guard per identity
    │   ├── router/
    │   │   ├── users.ts    # Router<typeof contract.routes.users>
    │   │   ├── events.ts
    │   │   ├── health.ts
    │   │   └── index.ts    # server.router, composes the groups
    │   ├── jobs.ts         # server.jobs
    │   └── api.ts          # server.api, what you mount
    ├── lib/
    │   └── api-client.ts   # new KizunaClient(contract)
    └── app/
        └── api/[...ts-kizuna]/route.ts   # api.mount(), re-exports the handlers
```

The rule is the same at any size: one contract, imported by both sides, with no server-only code in it.

### The `@/` alias

Examples throughout these docs import from `@/contract` and `@/server/api`. That is `@/` pointing at `src/`, which `create-next-app` sets up for you. Anywhere else, declare it yourself:

```json title="tsconfig.json"
{
    "compilerOptions": {
        "paths": {
            "@/*": ["./src/*"]
        }
    }
}
```
