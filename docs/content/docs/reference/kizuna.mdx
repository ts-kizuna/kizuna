title: kizuna
description: Create the typed factory for one API surface — its tags, validation codes, route groups, and contract.

`kizuna` builds the typed factory for one API. Destructure `k` from it, then use `k.routes` to define route groups and `k.contract` to assemble them. Set it up once and import `k` wherever you define routes.

<InstallTabs packageName="@ts-kizuna/core" />

```ts
import { kizuna } from '@ts-kizuna/core';
```

## Parameters

```ts
kizuna(config?: {
    identities?: Record<string, Identity>;
    requestContext?: Record<string, RequestContext>;
    tags?: TagSet;
    validation?: { issueCodes?: readonly string[] };
}): { k: K }
```

| Field                   | Type                             | Description                                                                                                                                                    |
| ----------------------- | -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `identities`            | `Record<string, Identity>`       | Optional. The API's identities from the [`createIdentity` builders](/docs/reference/create-identity). The keys become the names the `auth` map and guards use. |
| `requestContext`        | `Record<string, RequestContext>` | Optional. Declarations from [`createRequestContext`](/docs/reference/create-request-context) — request-scoped values every handler receives.                   |
| `tags`                  | `TagSet`                         | Optional. A tag set from [`createTags`](/docs/reference/create-tags). Its keys become the allowed group tags.                                                  |
| `validation.issueCodes` | `readonly string[]`              | Optional. Custom validation issue codes this API's handlers may emit via `addCodedIssue`. Captured as a literal union.                                         |

## Returns

`{ k }`, the factory for this API:

| Method       | Signature                        | Description                                                |
| ------------ | -------------------------------- | ---------------------------------------------------------- |
| `k.routes`   | `(tag, defs) => Routes`          | Define a route group under one of the tag set's keys.      |
| `k.contract` | `({ routes, auth }) => Contract` | Assemble route groups into the contract shared everywhere. |

## Example

Set the factory up once — usually in a `k.ts` file — then import `k` wherever you define routes.

```ts
// k.ts
import { kizuna } from '@ts-kizuna/core';
import { tags } from './tags';
import { user, member } from './identities';
import { analytics } from './request-contexts';

export const { k } = kizuna({
    identities: {
        user,
        member,
    },
    requestContext: {
        analytics,
    },
    tags,
    validation: {
        issueCodes: ['invalid_phone_number'],
    },
});
```

## Defining route groups

`k.routes(tag, defs)` defines a group of routes under one tag. The tag must be a key of the set you passed to `kizuna`, and TypeScript completes it.

```ts
// routes.ts
import { z } from 'zod';
import { k } from './k';

export const usersRoutes = k.routes('users', {
    listUsers: {
        method: 'GET',
        path: '/users',
        query: z.object({
            page: z.number().int().min(1).default(1),
            limit: z.number().int().min(1).max(100).default(10),
        }),
        responses: {
            200: z.object({
                users: z.array(UserSchema),
                total: z.number(),
            }),
        },
    },
    createUser: {
        method: 'POST',
        path: '/users',
        body: z.object({
            name: z.string().min(1),
            email: z.email(),
        }),
        responses: {
            201: UserSchema,
            400: ProblemDetailsSchema,
        },
    },
    getUser: {
        method: 'GET',
        path: '/users/:id',
        responses: {
            200: UserSchema,
            404: ProblemDetailsSchema,
        },
    },
});
```

### Route definition fields

| Field         | Required | Type                                                                                           |
| ------------- | -------- | ---------------------------------------------------------------------------------------------- |
| `method`      | Yes      | `'GET'` `'POST'` `'PUT'` `'PATCH'` `'DELETE'` `'HEAD'` `'OPTIONS'`                             |
| `path`        | Yes      | URL path — use `:name` for path parameters                                                     |
| `body`        | —        | Zod schema for the request body                                                                |
| `query`       | —        | Zod schema for the query string                                                                |
| `headers`     | —        | Zod schema for request headers                                                                 |
| `responses`   | Yes      | Response schemas keyed by status code                                                          |
| `contentType` | —        | `'application/json'` (default), `'multipart/form-data'`, `'application/x-www-form-urlencoded'` |
| `summary`     | —        | Short description shown in OpenAPI                                                             |
| `tags`        | —        | OpenAPI tag keys (from the tag set), resolved to titles in the spec                            |

Auth is deliberately absent from this table. A route's `security` is owned by the contract's `auth` map — writing `security` inline in `k.routes` is a type error. This keeps the whole API's auth policy in one place instead of scattered across route files.

## Assembling the contract

`k.contract({ routes, auth })` bundles your route groups into the `Contract` — the one object you hand to the [client](/docs/reference/create-client), [server](/docs/reference/create-api), and generators. It carries the routes, the auth resolved onto them, plus the tags, identities, and `issueCodes` you configured on `kizuna`.

```ts
// contract.ts
import { k } from './k';
import { usersRoutes } from './routes';

export const contract = k.contract({
    routes: {
        users: usersRoutes,
    },
    auth: {
        users: false,
    },
});
```

The declared `issueCodes` widen `errors[].code` on `400` responses to `ValidationIssueCode | <your codes>`, so the client suggests them in autocomplete. Emit them at runtime with [`addCodedIssue`](/docs/reference/add-coded-issue). Because the factory is per API, codes and tags stay scoped to their API rather than leaking across the multiple kizuna APIs a project may define.

## The auth map

The `auth` map assigns each route group its auth policy, keyed by the identity names registered on `kizuna`. It is **exhaustive over groups** — every key in `routes` must appear, and public takes an explicit `false`, so a new group can't ship unsecured by omission. For the full walkthrough, see the [Auth guide](/docs/auth).

```ts
export const contract = k.contract({
    routes,
    auth: {
        users: false,
        health: false,
        members: {
            '*': 'user',
            inviteMember: {
                member: {
                    role: ['owner', 'admin'],
                },
            },
        },
        workspace: {
            '*': 'member',
            deleteWorkspace: {
                member: {
                    role: 'owner',
                },
            },
        },
    },
});
```

### Value forms

| Form                           | Example                                     | Meaning                                                                                                                           |
| ------------------------------ | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `false`                        | `health: false`                             | Public — no guard runs.                                                                                                           |
| Identity name                  | `members: 'user'`                           | Require the identity. Its guard runs; handlers receive its context.                                                               |
| Constraint object              | `{ member: { role: 'owner' } }`             | Require the identity **and** gate its `access` fields — out-of-range values get a 403, in-range values narrow the handler's type. |
| Constraint with allowed values | `{ member: { role: ['owner', 'admin'] } }`  | Gate a field to a set of values.                                                                                                  |
| Scope array (`oauth2`)         | `{ user: ['users:write'] }`                 | Require the identity with these OAuth scopes.                                                                                     |
| Multiple identities            | `{ user: true, member: { role: 'owner' } }` | Require every listed identity (AND). Handlers receive each context.                                                               |

### Cascades

A group's value can be a cascade — `'*'` sets the group default, and a route entry refines it: the route inherits the default's identities and states only its delta. `false` opts a route out.

```ts
workspace: {
    '*': 'member',
    deleteWorkspace: {
        member: {
            role: 'owner',
        },
    },
},
```

Every route under `workspace` requires `member`; `deleteWorkspace` additionally gates on `role: 'owner'` — and inside its handler, `auth.member.role` is typed `'owner'`.

`k.contract` resolves the map onto every route's `security` (and `accessGate` where fields are constrained), which the [guards](/docs/reference/create-guard), [router](/docs/reference/create-router) types, and [OpenAPI spec](/docs/reference/generate-openapi) all read.

### `k.auth`

`k.auth(routes, map)` returns the map typed against the routes and identities, for when you'd rather define it beside the routes than inline in `k.contract`:

```ts
export const auth = k.auth(routes, {
    users: false,
    members: 'user',
});

export const contract = k.contract({
    routes,
    auth,
});
```

## Request context

`requestContext` registers declarations from [`createRequestContext`](/docs/reference/create-request-context) — request-scoped values like analytics ids or a logger. Every handler receives them typed under `requestContext`, keyed by their name; each is resolved per request by a [`createRequestContextResolver`](/docs/reference/create-request-context) wired on `createApi`.

```ts title="request-contexts.ts"
import { z } from 'zod';
import { createRequestContext } from '@ts-kizuna/core';

export const analytics = createRequestContext(
    z.object({
        sessionId: z.string().nullable(),
    })
);
```

```ts title="k.ts"
import { analytics } from './request-contexts';

export const { k } = kizuna({
    requestContext: {
        analytics,
    },
});
```

```ts
listUsers: ({ query, requestContext }) => {
    track(requestContext.analytics.sessionId, 'listUsers');
    // ...
},
```
