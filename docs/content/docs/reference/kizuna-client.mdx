Create a fully typed HTTP client from a contract. See the [fetch client guide](/docs/clients/fetch) for usage.

<InstallTabs packageName="@ts-kizuna/fetch" />

```ts
import { KizunaClient } from '@ts-kizuna/fetch';
```

## Parameters

```ts
new KizunaClient(contract: Contract, config: ClientConfig): Client
```

| Parameter  | Type           | Description                                                  |
| ---------- | -------------- | ------------------------------------------------------------ |
| `contract` | `Contract`     | The contract from [`k.contract`](/docs/reference/k-contract) |
| `config`   | `ClientConfig` | Client configuration                                         |

## `ClientConfig`

| Option           | Type                                 | Required | Description                                                                                                                                                                      |
| ---------------- | ------------------------------------ | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `baseUrl`        | `string`                             | Yes      | Base URL prepended to every route path                                                                                                                                           |
| `baseHeaders`    | `Record<string, string>`             | No       | Headers merged into every request                                                                                                                                                |
| `credentials`    | `RequestCredentials`                 | No       | Passed as `credentials` to every `fetch` call                                                                                                                                    |
| `fetch`          | `typeof fetch`                       | No       | Custom fetch implementation (e.g. for testing or a polyfill)                                                                                                                     |
| `onRequest`      | `(context) => void \| Promise<void>` | No       | Callback before each request, receiving `{ url, method, headers, route }`. May be async.                                                                                         |
| `requestContext` | `ContextHeaderInputs`                | \*       | Header values for the contract's [request context](/docs/reference/kizuna-request-context). Present only when the contract declares one, and required when any of its headers is |

`requestContext` values are typed from the declared header schemas, so an optional header stays optional and a coerced one takes the schema's input type.

## Returns

`new KizunaClient()` returns the `Client`, mirroring the contract's route groups. Each route becomes a function accepting `{ params?, query?, body?, headers?, fetchOptions? }` and returning a `Promise` resolving to `{ status, body, headers }`.

`params` is typed from the route's `pathParams` schema output when one is declared (matching the server-side handler), otherwise from the `:param` placeholders in the path.

The response is a discriminated union over the route's declared status codes. Narrow on `status` to access the correctly typed `body`.

## Example

When the contract secures routes with [identities](/docs/authentication), send the credential in `baseHeaders`:

```ts
import { KizunaClient } from '@ts-kizuna/fetch';
import { contract } from './contract';

const apiClient = new KizunaClient(contract, {
    baseUrl: 'http://localhost:3000',
    baseHeaders: {
        Authorization: `Bearer ${token}`,
    },
});

const result = await apiClient.routes.users.createUser({
    body: {
        name: 'Alice',
        email: 'alice@example.com',
    },
});

if (result.status === 201) {
    console.log(result.body.id);
} else {
    console.error(result.body.detail);
}
```

## routes

Every route lives under `routes`, mirroring the contract's own groups. The client's own accessors, such as [`permissions`](#permissions), sit beside it rather than inside it, so a route group may be named anything the contract needs without colliding with them.

```ts
await apiClient.routes.members.listMembers();
await apiClient.permissions();
```

## Per-request options

Pass `fetchOptions` to customize individual requests:

```ts
const { body } = await client.routes.users.listUsers({
    query: {
        page: 1,
    },
    fetchOptions: {
        signal: AbortSignal.timeout(5000),
    },
});
```

See the [Fetch client guide](/docs/clients/fetch) for per-request headers, validation errors, and response type narrowing.

## permissions

When the contract declares a [permissions endpoint](/docs/access-control#the-client), the client carries a `permissions()` accessor. It fetches the caller's coarse rules once and hands back a reader over them:

```ts
const { hasPermission } = await apiClient.permissions();

if (hasPermission('events:read')) {
    // show the event log tab
}
```

`hasPermission` takes the same `resource:action` name a route gate takes, narrowed to the declared union, so a permission is spelled one way across the contract, the server and here.

Only permissions applying to no record cross the wire, so this is enough to hide an action the caller cannot perform and never enough to decide about one specific record. Those stay on the server, behind `permission.group.name(record)` in a handler.
