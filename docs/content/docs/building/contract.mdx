The contract is the source of truth for your API. You hand it to [`new KizunaServer()`](/docs/building/router) on the server and [`new KizunaClient()`](/docs/clients/fetch) on every client.

<ContractNotice />

## Create the factory

Construct it once, usually in a `k.ts` file, and export `k`. Pass a tag set so route groups have a tag to sit under, where the keys become the allowed group names.

```ts title="k.ts"
import { Kizuna } from '@ts-kizuna/core';

const tags = Kizuna.tags({
    users: 'Users',
});

export const k = new Kizuna({
    tags,
});
```

## Define your routes

Call `k.routes` with a tag and your routes.

```ts title="users.ts"
import { z } from 'zod';
import { ProblemDetailsSchema } from '@ts-kizuna/core/schemas';
import { k } from './k';

export const UserSchema = z.object({
    id: z.string(),
    name: z.string(),
    email: z.email(),
});

export const usersRoutes = k.routes('users', {
    listUsers: {
        method: 'GET',
        path: '/users',
        query: z.object({
            page: z.number().int().min(1).default(1),
            limit: z.number().int().min(1).max(100).default(10),
        }),
        responses: {
            200: z.object({
                users: z.array(UserSchema),
                total: z.number(),
            }),
        },
    },
    createUser: {
        method: 'POST',
        path: '/users',
        body: z.object({
            name: z.string().min(1),
            email: z.email(),
        }),
        responses: {
            201: UserSchema,
            400: ProblemDetailsSchema,
        },
    },
    getUser: {
        method: 'GET',
        path: '/users/:id',
        responses: {
            200: UserSchema,
            404: ProblemDetailsSchema,
        },
    },
});
```

### Route fields

| Field         | Required | Description                                                                                    |
| ------------- | -------- | ---------------------------------------------------------------------------------------------- |
| `method`      | Yes      | `GET` `POST` `PUT` `PATCH` `DELETE` `HEAD` `OPTIONS`                                           |
| `path`        | Yes      | URL path. Use `:name` for path parameters                                                      |
| `responses`   | Yes      | Response schemas keyed by status code                                                          |
| `pathParams`  | No       | Path parameter schema, keyed by placeholder name                                               |
| `body`        | No       | Request body schema                                                                            |
| `query`       | No       | Query string schema                                                                            |
| `headers`     | No       | Request headers schema                                                                         |
| `contentType` | No       | `'application/json'` (default), `'multipart/form-data'`, `'application/x-www-form-urlencoded'` |
| `summary`     | No       | Short description shown in OpenAPI                                                             |
| `tags`        | No       | OpenAPI tags                                                                                   |

### Typing path parameters

Path parameters are strings unless you say otherwise. Add `pathParams` to parse and validate them:

```ts
getUser: {
    method: 'GET',
    path: '/users/:id',
    pathParams: z.object({
        id: z.uuid(),
    }),
    responses: {
        200: UserSchema,
    },
},
```

Each value must be a scalar, since a path segment arrives as one string. Structured values belong in `query`. To parse one into something richer, use `z.string().transform(...)`:

```ts
pathParams: z.object({
    tags: z.string().transform((value) => value.split(',')),
}),
```

## Query, path, and header coercion

Values in the URL and in headers always arrive as strings. ts-kizuna coerces them to the types you declare, so both the client and the server see the parsed value:

| Declare                  | Accepts on the wire  | You get             |
| ------------------------ | -------------------- | ------------------- |
| `z.number()` / `z.int()` | `"42"`               | `42`                |
| `z.boolean()`            | `"true"` / `"false"` | `true` / `false`    |
| `z.bigint()`             | `"9007199254740993"` | `9007199254740993n` |
| `z.date()`               | an ISO 8601 string   | `Date`              |

Arrays of these coerce too (`z.array(z.number())`). The fetch client serializes `Date` and `bigint` values for you, so a `z.date()` query param round-trips without manual formatting.

Because coercion is built in, **`z.coerce` is not supported**, and `k.routes` throws if any schema uses it. Declare the plain schema (`z.number()`, `z.date()`, `z.bigint()`). To receive a different type than you send, use `z.string().transform(...)`.

### Response schemas

One Zod schema per status code:

```ts
responses: {
    200: UserSchema,
    404: ProblemDetailsSchema,
},
```

Use `z.void()` for a status that carries no body:

```ts
responses: {
    204: z.void(),
    404: ProblemDetailsSchema,
},
```

To type response headers, give the status a `{ body, headers }` object:

```ts
responses: {
    200: {
        body: UserSchema,
        headers: z.object({
            'x-request-id': z.string().optional(),
        }),
    },
},
```

## Native types in bodies

Bodies carry native types too, nested at any depth. The wire stays plain JSON, and the OpenAPI document describes exactly what crosses it:

| Declare      | On the wire        | OpenAPI               | You get  |
| ------------ | ------------------ | --------------------- | -------- |
| `z.date()`   | an ISO 8601 string | `string`, `date-time` | `Date`   |
| `z.bigint()` | a JSON integer     | `integer`, `int64`    | `bigint` |
| `UrlSchema`  | the absolute URL   | `string`, `uri`       | `URL`    |
| `z.file()`   | a multipart part   | `string`, `binary`    | `File`   |

Both directions revive: a handler receives a `z.date()` body field as a `Date`, and the fetch client hands a `z.date()` response field back as a `Date`. The Swift client sees `Date`, `Int64`, and `URL`; the Kotlin client `Instant`, `Long`, and `String`.

A `bigint` crosses the wire as a JSON integer with its exact digits, beyond `Number.MAX_SAFE_INTEGER` included, in every response and in bodies the fetch client sends or receives. Two bounds remain: a request body parsed by the server framework's own `JSON.parse` is exact up to ±2^53, and a browser without `JSON.rawJSON` (Baseline 2025) sends larger values as an error instead of rounding them silently.

Fields inside plain `z.union(...)` options pass through unconverted; `z.discriminatedUnion(...)` variants revive like any other object. The full behavior, bounds included, is in [Native types](/docs/reference/native-types).

## Bundle into a contract

Assemble your route groups with `k.contract` and default-export the result. This is the object `client` and `server.api` consume.

```ts title="contract/index.ts"
import { k } from './k';
import { usersRoutes } from './routes';

export const contract = k.contract({
    routes: {
        users: usersRoutes,
    },
});
```

API-wide settings are configured on `new Kizuna()` and carried onto every contract `k.contract` produces, so you set them once. That covers tags and [`validation.issueCodes`](/docs/reference/k-issue) for custom validation codes.

For non-JSON responses, set `contentType` to send the body as-is instead of JSON. Responses default to `application/json`, and errors to `application/problem+json`. Declare a non-JSON body as `z.string()`:

```ts
responses: {
    200: {
        body: z.string(),
        contentType: 'text/csv',
    },
},
```

For binary responses, use [`BinarySchema`](/docs/reference/binary-and-file-schemas) for a body of raw bytes (`Uint8Array`/`Buffer`), such as a PDF download:

```ts title="reports.ts"
import { BinarySchema } from '@ts-kizuna/core/schemas';

responses: {
    200: {
        body: BinarySchema,
        contentType: 'application/pdf',
    },
},
```

## Authentication

Authentication is part of the contract too: you declare identities with [`Kizuna.identity`](/docs/reference/kizuna-identity), register them on `new Kizuna()`, and give `k.contract` an `auth` map saying which routes require which identity. That one declaration drives runtime enforcement, typed handler context, and the OpenAPI spec's security. The [Authentication guide](/docs/authentication) walks the whole pipeline.

## Jobs

Scheduled work is declared on the contract too. [`k.jobs`](/docs/reference/k-jobs) takes the identity every job requires and the jobs themselves, and the result goes under `jobs` on `k.contract`, beside `routes`:

```ts title="contract/index.ts"
export const contract = k.contract({
    routes: {
        users: usersRoutes,
    },
    jobs,
});
```

A job carries its own identity, so it takes no entry in the `auth` map, and it stays out of `contract.routes`, the OpenAPI document, and the generated Swift, Kotlin, and MCP surfaces. The [Jobs guide](/docs/jobs) covers declaring, handling, and triggering them.

## Going further

### Naming schemas with models

By default the generators inline each schema wherever it appears. Use [`Kizuna.model`](/docs/reference/kizuna-model) to give a schema a name they can reuse:

```ts title="users.ts"
import { Kizuna } from '@ts-kizuna/core';

export const UserSchema = Kizuna.model({
    title: 'User',
    description: 'A user in the system',
    schema: z.object({
        id: z.string(),
        name: z.string(),
        email: z.email(),
    }),
});
```

- **OpenAPI**: extracted into `components.schemas.User`, and every usage becomes a `$ref`
- **Swift**: emitted as a shared `public struct User`
- **TypeScript**: pair it with an exported type (see [Exporting types](#exporting-types))

### Splitting routes across files

Large contracts split into groups. Declare the tags once with [`Kizuna.tags`](/docs/reference/kizuna-tags), pass them to `new Kizuna()`, then define each group with `k.routes` in its own file:

```ts title="tags.ts"
import { Kizuna } from '@ts-kizuna/core';

export const tags = Kizuna.tags({
    users: {
        title: 'Users',
        description: 'User management endpoints',
    },
    health: 'Health',
});
```

```ts title="k.ts"
import { Kizuna } from '@ts-kizuna/core';
import { tags } from './tags';

export const k = new Kizuna({
    tags,
});
```

```ts title="users.ts"
import { k } from '../k';

export const usersRoutes = k.routes('users', {
    listUsers: { ... },
    createUser: { ... },
});
```

An `index.ts` beside them collects the groups, so the contract has one import to make:

```ts title="routes/index.ts"
import { usersRoutes } from './users';
import { healthRoutes } from './health';

export const routes = {
    users: usersRoutes,
    health: healthRoutes,
};
```

```ts title="contract/index.ts"
import { k } from './k';
import { routes } from './routes';

export const contract = k.contract({
    routes,
});
```

See [Project Structure](/docs/project-structure) for where the rest of the pieces go.

The group tag's `title` becomes the OpenAPI tag for every route in the group, and the `description` is included in the tag definition. A route can also cross-tag by listing tag keys directly:

```ts
cancelAccount: {
    method: 'POST',
    path: '/account/cancel',
    tags: ['users', 'health'],
    // ...
},
```

### Deprecating routes and fields

Set `deprecated` on a route, either `true` or a migration message:

```ts
deleteUser: {
    method: 'DELETE',
    path: '/users/:id',
    deprecated: 'use `archiveUser` instead',
    responses: {
        200: z.object({
            success: z.boolean(),
        }),
    },
},
```

Fields declare it in their [Zod metadata](https://zod.dev/metadata), with the same `true | string` shape:

```ts
getUser: {
    method: 'GET',
    path: '/users/:id',
    responses: {
        200: z.object({
            id: z.string(),
            name: z.string(),
            legacyUsername: z.string().optional().meta({
                deprecated: 'use name instead',
            }),
        }),
    },
},
```

The OpenAPI spec and the Swift and Kotlin clients pick both up. A route also takes a deprecation `date` and a `sunset` timestamp, both ISO 8601, and every response from it then announces them in the `Deprecation` and `Sunset` headers. See [Deprecations](/docs/deprecations).

### Exporting types

Infer TypeScript types from your schemas in a separate `types.ts` so consumers can import them without pulling in runtime code:

```ts title="types.ts"
import type { z } from 'zod';
import { UserSchema, CreateUserSchema } from './routes';

export type User = z.infer<typeof UserSchema>;
export type CreateUserInput = z.infer<typeof CreateUserSchema>;
```

```tsx title="UserCard.tsx"
import type { User } from '@/contract/types';

function UserCard({ user }: { user: User }) {
    return <div>{user.name}</div>;
}
```
