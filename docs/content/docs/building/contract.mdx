The contract is the source of truth for your API. Building one is three small steps:

1. **`kizuna`** — create the typed factory once and destructure `k`.
2. **`k.routes`** — describe each endpoint in a group: method, path, and Zod schemas.
3. **`k.contract`** — bundle those groups (plus optional settings) into the object you share everywhere.

You hand the result to [`createRouter`](/docs/building/router) on the server and [`createClient`](/docs/clients/fetch) on every client. This page covers defining it; the [Router](/docs/building/router) and [Mounting](/docs/building/mounting) pages cover implementing and serving it.

## Create the factory

Set up `kizuna` once — usually in a `k.ts` file — and export `k`. Pass a tag set so route groups have a tag to sit under; the keys become the allowed group names. Then import `k` wherever you define routes.

```ts title="packages/contract/src/k.ts"
import { kizuna, createTags } from '@ts-kizuna/core';

const tags = createTags({
    users: 'Users',
});

export const { k } = kizuna({
    tags,
});
```

## Define your routes

Call `k.routes` with a tag and your routes. For each one, pick a method and path, then describe what it takes in (`body`, `query`, `headers`) and what it sends back (`responses`) with Zod schemas.

```ts title="packages/contract/src/routes.ts"
import { z } from 'zod';
import { ProblemDetailsSchema } from '@ts-kizuna/core/schemas';
import { k } from './k';

export const UserSchema = z.object({
    id: z.string(),
    name: z.string(),
    email: z.email(),
});

export const usersRoutes = k.routes('users', {
    listUsers: {
        method: 'GET',
        path: '/users',
        query: z.object({
            page: z.number().int().min(1).default(1),
            limit: z.number().int().min(1).max(100).default(10),
        }),
        responses: {
            200: z.object({
                users: z.array(UserSchema),
                total: z.number(),
            }),
        },
    },
    createUser: {
        method: 'POST',
        path: '/users',
        body: z.object({
            name: z.string().min(1),
            email: z.email(),
        }),
        responses: {
            201: UserSchema,
            400: ProblemDetailsSchema,
        },
    },
    getUser: {
        method: 'GET',
        path: '/users/:id',
        responses: {
            200: UserSchema,
            404: ProblemDetailsSchema,
        },
    },
});
```

### Route fields

| Field         | Required | Description                                                                                    |
| ------------- | -------- | ---------------------------------------------------------------------------------------------- |
| `method`      | Yes      | `GET` `POST` `PUT` `PATCH` `DELETE` `HEAD` `OPTIONS`                                           |
| `path`        | Yes      | URL path — use `:name` for path parameters                                                     |
| `responses`   | Yes      | Response schemas keyed by status code                                                          |
| `pathParams`  | —        | Path parameter schema, keyed by placeholder name                                               |
| `body`        | —        | Request body schema                                                                            |
| `query`       | —        | Query string schema                                                                            |
| `headers`     | —        | Request headers schema                                                                         |
| `contentType` | —        | `'application/json'` (default), `'multipart/form-data'`, `'application/x-www-form-urlencoded'` |
| `summary`     | —        | Short description shown in OpenAPI                                                             |
| `tags`        | —        | OpenAPI tags                                                                                   |

### Typing path parameters

Path parameters are strings unless you say otherwise. Add `pathParams` to parse and validate them:

```ts
getUser: {
    method: 'GET',
    path: '/users/:id',
    pathParams: z.object({
        id: z.uuid(),
    }),
    responses: {
        200: UserSchema,
    },
},
```

The keys must be exactly the `:name` placeholders in the path, so a typo like `/users/:usrId` is a type error on `pathParams`.

Each value must be a scalar, since a path segment arrives as one string. Structured values belong in `query`. To parse one into something richer, use `z.string().transform(...)`:

```ts
pathParams: z.object({
    tags: z.string().transform((value) => value.split(',')),
}),
```

## Query, path, and header coercion

Values in the URL and in headers always arrive as strings. ts-kizuna coerces them to the types you declare, so you write the schema you actually mean and get the parsed value on both the client and the server:

| Declare                  | Accepts on the wire  | You get             |
| ------------------------ | -------------------- | ------------------- |
| `z.number()` / `z.int()` | `"42"`               | `42`                |
| `z.boolean()`            | `"true"` / `"false"` | `true` / `false`    |
| `z.bigint()`             | `"9007199254740993"` | `9007199254740993n` |
| `z.date()`               | an ISO 8601 string   | `Date`              |

Arrays of these coerce too (`z.array(z.number())`). The fetch client serializes `Date` and `bigint` values for you, so a `z.date()` query param round-trips without any manual formatting. Request bodies are sent as JSON and keep their types, so they are never coerced.

Because coercion is built in, **`z.coerce` is not supported** — `k.routes` throws if any schema uses it. Use the plain schema (`z.number()`, `z.date()`, `z.bigint()`) instead. When you genuinely want to receive a different type than you send, `z.string().transform(...)` is the explicit, type-safe way to do it.

### Response schemas

The simple form is one Zod schema per status code:

```ts
responses: {
    200: UserSchema,
    404: ProblemDetailsSchema,
},
```

Use `z.void()` for a status that carries no body:

```ts
responses: {
    204: z.void(),
    404: ProblemDetailsSchema,
},
```

To type response headers, give the status a `{ body, headers }` object:

```ts
responses: {
    200: {
        body: UserSchema,
        headers: z.object({
            'x-request-id': z.string().optional(),
        }),
    },
},
```

## Bundle into a contract

Assemble your route groups with `k.contract` and default-export the result. This is the object `client` and `createApi` consume.

```ts title="packages/contract/src/contract.ts"
import { k } from './k';
import { usersRoutes } from './routes';

export const contract = k.contract({
    routes: {
        users: usersRoutes,
    },
});
```

API-wide settings — tags and [`validation.issueCodes`](/docs/reference/add-coded-issue) for custom validation codes — are configured on `kizuna` and carried onto every contract `k.contract` produces, so you set them once.

Non-JSON responses — set `contentType` to send the body as-is instead of JSON. Responses default to `application/json` (errors to `application/problem+json`); declare a non-JSON body as `z.string()`:

```ts
responses: {
    200: {
        body: z.string(),
        contentType: 'text/csv',
    },
},
```

Binary responses — use [`BinarySchema`](/docs/reference/binary-and-file-schemas) for a body of raw bytes (`Uint8Array`/`Buffer`), e.g. a PDF download:

```ts
import { BinarySchema } from '@ts-kizuna/core/schemas';

responses: {
    200: {
        body: BinarySchema,
        contentType: 'application/pdf',
    },
},
```

That's everything you need to define an API. The rest of this page is optional — reach for it when you need it.

## Auth

Auth is part of the contract too: you declare identities with [`createIdentity`](/docs/reference/create-identity), register them on `kizuna`, and give `k.contract` an `auth` map saying which routes require which identity. That one declaration drives runtime enforcement, typed handler context, the OpenAPI spec's security, and client-side access checks. The [Auth guide](/docs/auth) walks the whole pipeline.

## Going further

### Naming schemas with models

By default the generators inline each schema wherever it appears. Use [`createModel`](/docs/reference/create-model) to give a schema a name they can reuse:

```ts
import { createModel } from '@ts-kizuna/core';

export const UserSchema = createModel({
    title: 'User',
    description: 'A user in the system',
    schema: z.object({
        id: z.string(),
        name: z.string(),
        email: z.email(),
    }),
});
```

- **OpenAPI** — extracted into `components.schemas.User`; every usage becomes a `$ref`
- **Swift** — emitted as a shared `public struct User`
- **TypeScript** — pair it with an exported type (see [Exporting types](#exporting-types))

### Splitting routes across files

Large contracts split into groups. Declare the tags once with [`createTags`](/docs/reference/create-tags), pass them to `kizuna`, then define each group with `k.routes` in its own file:

```ts title="contract/tags.ts"
import { createTags } from '@ts-kizuna/core';

export const tags = createTags({
    users: {
        title: 'Users',
        description: 'User management endpoints',
    },
    health: 'Health',
});
```

```ts title="contract/k.ts"
import { kizuna } from '@ts-kizuna/core';
import { tags } from './tags';

export const { k } = kizuna({
    tags,
});
```

```ts title="contract/users.ts"
import { k } from './k';

export const usersRoutes = k.routes('users', {
    listUsers: { ... },
    createUser: { ... },
});
```

```ts title="contract/contract.ts"
import { k } from './k';
import { usersRoutes } from './users';
import { healthRoutes } from './health';

export const contract = k.contract({
    routes: {
        users: usersRoutes,
        health: healthRoutes,
    },
});
```

The group tag's `title` becomes the OpenAPI tag for every route in the group; the `description` is included in the tag definition. A route can also cross-tag by listing tag keys directly:

```ts
cancelAccount: {
    method: 'POST',
    path: '/account/cancel',
    tags: ['users', 'health'],
    // ...
},
```

### Deprecating routes and fields

Add a `/** @deprecated */` JSDoc tag above a route or a response field — optionally with a message, `/** @deprecated use createUser instead */`.

```ts
/**
 * @deprecated
 */
deleteUser: {
    method: 'DELETE',
    path: '/users/:id',
    responses: {
        200: z.object({
            success: z.boolean(),
        }),
    },
},
```

```ts
getUser: {
    method: 'GET',
    path: '/users/:id',
    responses: {
        200: z.object({
            id: z.string(),
            name: z.string(),
            /**
             * @deprecated
             */
            legacyUsername: z.string().optional(),
        }),
    },
},
```

IDEs show a strikethrough on deprecated routes and fields right away. To carry the tags into the OpenAPI spec and Swift client, add the one-time build step in [Deprecations](/docs/deprecations).

### Exporting types

Infer TypeScript types from your schemas in a separate `types.ts` so consumers can import them without pulling in runtime code:

```ts title="packages/contract/src/types.ts"
import type { z } from 'zod';
import { UserSchema, CreateUserSchema } from './routes';

export type User = z.infer<typeof UserSchema>;
export type CreateUserInput = z.infer<typeof CreateUserSchema>;
```

```ts
import type { User } from '@shared/contract/types';

function UserCard({ user }: { user: User }) {
    return <div>{user.name}</div>;
}
```
