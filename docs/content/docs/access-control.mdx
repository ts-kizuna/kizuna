title: Access Control
description: Name every permission that exists, bundle them into roles, and say which one each route needs. kizuna checks the caller's role against the route before the handler runs.
---

<BetaNotice>

Access control is still settling. `Kizuna.permissions`, `permissions.roles`, `roles.rules` and `k.accessControl` may change before v2, so pin your version if you depend on them.

</BetaNotice>

[Authentication](/docs/authentication) turns a credential into the caller. This page decides what that caller may do.

A user holds a role. A role holds permissions. A route needs one. kizuna checks that the role covers it before the handler runs.

<Steps>

<Step>

## Declare your permissions

A permission is one thing that can be done to one kind of thing. List every one that exists, grouped by what it acts on:

```ts title="contract/permissions.ts"
export const permissions = Kizuna.permissions({
    workspace: ['read', 'update', 'delete'],
    project: ['create', 'read', 'update', 'delete', 'share'],
    invite: ['send', 'cancel', 'accept'],
});
```

Use the verb the route uses, so an invite is `send` rather than `create`.

</Step>

<Step>

## Bundle them into roles

Every entry is checked against the list. `'all'` means every permission declared:

```ts title="contract/roles.ts"
export const roles = permissions.roles({
    member: {
        workspace: ['read'],
        project: ['read'],
    },
    admin: {
        workspace: ['read', 'update'],
        project: ['create', 'read', 'update', 'delete', 'share'],
        invite: ['send', 'cancel'],
    },
    owner: 'all',
});
```

Anything not listed is denied, so a new permission reaches no role until you add it.

Put the roles on the identity whose callers hold them:

```ts title="contract/identities.ts"
export const member = Kizuna.identity.apiKey({
    name: 'x-workspace-token',
    in: 'header',
    context: z.object({
        userId: z.string(),
        workspaceId: z.string(),
    }),
    roles,
});
```

That adds `role` to what the guard returns and what handlers receive, typed as `'member' | 'admin' | 'owner'`.

</Step>

<Step>

## Say what each route needs

Every group must appear in the map, so public is an explicit `false`. A route names the permission it needs:

```ts title="contract/access.ts"
export const access = k.accessControl(routes, {
    health: false,
    projects: {
        '*': {
            auth: 'member',
            requires: {
                project: ['read'],
            },
        },
        createProject: {
            auth: 'member',
            requires: {
                project: ['create'],
            },
        },
        deleteProject: {
            auth: 'member',
            requires: {
                project: ['delete'],
            },
        },
    },
    invites: {
        cancelInvite: {
            auth: 'member',
            requires: {
                invite: ['cancel'],
            },
        },
    },
});
```

```ts title="contract/index.ts"
export const contract = k.contract({
    routes,
    access,
});
```

A permission a route names must exist in the list, so a typo does not compile. Routes never name a role.

</Step>

<Step>

## Return the caller's role from the guard

The role is a column on the membership row or a claim in the token. The guard reads it:

```ts title="server/guards.ts"
export const requireMember = server.guard('member', async ({ apiKey, params, deny }) => {
    const membership = apiKey ? await findMembership(apiKey.value, params.workspaceId) : undefined;

    if (!membership) {
        return deny(403, 'Forbidden');
    }

    return {
        userId: membership.userId,
        workspaceId: membership.workspaceId,
        role: membership.role,
    };
});
```

kizuna checks that the role holds every permission the route requires and answers `403` before the handler otherwise.

A caller with several roles returns them as an array, and holds all of them. A caller granted more than their role says, rows in a table beside the role, returns those as `permissions` next to it:

```ts title="server/guards.ts"
return {
    userId: membership.userId,
    workspaceId: membership.workspaceId,
    role: membership.role,
    permissions: membership.grants,
};
```

kizuna checks the route against the role and the grants together.

</Step>

<Step>

## Check on the client (optional)

The contract carries the map and the roles, so the client answers from the caller's role with no request:

```ts title="projects-page.ts"
import { checkAccess } from '@ts-kizuna/fetch';

const access = checkAccess(contract, me.body.role);

if (access.projects.deleteProject) {
    showDeleteButton();
}
```

The result mirrors the route tree and each leaf is a boolean. [Checking on the client](#checking-on-the-client) covers where the role comes from.

</Step>

</Steps>

## What an entry can say

| Entry                          | Meaning                                            |
| ------------------------------ | -------------------------------------------------- |
| `false`                        | Public                                             |
| `'member'`                     | Requires the `member` identity, any permissions    |
| `{ auth, requires?, scopes? }` | The same, narrowed                                 |
| `{ '*': ..., login: false }`   | `'*'` is the group default, named keys override it |

`'member'` is shorthand for `{ auth: 'member' }`. A subgroup key covers its whole subtree, and can nest its own `'*'`. A key matching nothing in the group is an error.

## Rows are the handler's

A permission says whether the caller may call the route. It says nothing about one row, so whether this caller may update this project is decided in the handler, after the row is loaded, and which rows a query may see at all is decided inside the query. Three layers, each answering one question:

| Layer              | Runs                                    | Answers                                |
| ------------------ | --------------------------------------- | -------------------------------------- |
| Roles              | In the guard, before the handler        | May this role call this kind of route  |
| Rules              | In the handler, after the row is loaded | May this caller act on this row        |
| Row-level security | In the database, inside the query       | Which rows this request may see at all |

kizuna is the first layer and hands the handler `can` for the second. The third is the database's.

### One row

`roles.rules` takes the row type of each resource once and a function of the caller. The keys are the resources and verbs the permission list declared, so a rule for a permission that does not exist, or a permission with no rule, does not compile. An action is `true` when passing the access map is enough, and a predicate over the row when it comes down to ownership:

```ts title="server/rules.ts"
import type { Invite, Project, Workspace } from './db/schema';

export const rules = roles.rules<{
    workspace: Workspace;
    project: Project;
    invite: Invite;
}>((user) => {
    const isAdmin = user.role === 'admin' || user.role === 'owner';

    return {
        workspace: {
            read: true,
            update: true,
            delete: (workspace) => workspace.ownerId === user.userId,
        },
        project: {
            create: true,
            read: true,
            update: (project) => isAdmin || project.ownerId === user.userId,
            delete: (project) => isAdmin || project.ownerId === user.userId,
            share: (project) => isAdmin || project.ownerId === user.userId,
        },
        invite: {
            send: true,
            cancel: (invite) => isAdmin || invite.sentBy === user.userId,
            accept: true,
        },
    };
});
```

`user` is the caller the guard returns for the identity these roles are on, so `user.role` is `'member' | 'admin' | 'owner'`. Each predicate's parameter is the row type named for its resource.

Register the rules beside the guards:

```ts title="server/api.ts"
export const api = server.api({
    router,
    guards: {
        member: requireMember,
    },
    rules,
});
```

Every guarded handler then receives `can`, bound to the caller the guard returned. It takes the action first, then the resource, then the row. An action or resource the list does not name does not compile, and the row has to be that resource's row.

The handler loads the row, answers `404` when there is none, and asks before writing:

```ts title="server/router/projects.ts"
updateProject: async ({ auth, params, can, body }) => {
    const project = await db.query.projects.findFirst({
        where: eq(projects.id, params.projectId),
    });

    if (!project) {
        return {
            status: 404,
            body: {
                detail: 'Project not found',
            },
        };
    }

    if (!can('update', 'project', project)) {
        return {
            status: 403,
            body: {
                detail: 'Only the owner can update this project',
            },
        };
    }

    return {
        status: 200,
        body: await saveProject(project.id, body),
    };
},
```

The role check ran in the guard, so the handler checks ownership alone. `roles` says which routes a role may call, `rules` says which rows a caller may touch, and a rule only runs for a caller whose role already passed the route.

`can(action, resource, row)` is the whole surface a handler sees. The rules behind it can grow, to a folder a project inherits from or to an engine that answers over a graph, without a handler changing.

### Every row

<Callout type="warn" title="kizuna cannot enforce a tenant filter">
    It runs before the query, never inside it. A list that forgets its `where` returns every tenant's rows.
</Callout>

Postgres row-level security enforces it at the one layer that sees every query:

```sql title="migrations/0007_projects_rls.sql"
alter table projects enable row level security;
alter table projects force row level security;

create policy "own workspace" on projects
    using (workspace_id = current_setting('app.workspace_id', true));
```

`force` applies the policy to the table's owner as well, so it holds when the app connects as the role that ran the migration. The `true` on `current_setting` makes a request that set nothing see no rows, where the default would fail the query.

Set the id per request, inside a transaction, with the third argument of `set_config` `true` so the value is local to that transaction:

```ts title="server/db/with-workspace.ts"
export const withWorkspace = <Result>(workspaceId: string, run: (tx: Transaction) => Promise<Result>) =>
    db.transaction(async (tx) => {
        await tx.execute(sql`select set_config('app.workspace_id', ${workspaceId}, true)`);

        return run(tx);
    });
```

```ts title="server/router/projects.ts"
listProjects: async ({ auth }) => ({
    status: 200,
    body: {
        projects: await withWorkspace(auth.member.workspaceId, (tx) => tx.query.projects.findMany()),
    },
}),
```

A pooled connection serves the next request the moment this one ends. A session-level `set` rides along with it, and a transaction-local one ends with the transaction.

## Scopes

An oauth2 identity carries the scopes its token was granted. A route can require one:

```ts title="contract/access.ts"
events: {
    listEvents: {
        auth: 'user',
        scopes: ['read:events'],
    },
},
```

A scope is what the token may attempt and `requires` is what the person may do, so a route can carry both. See [OAuth](/docs/oauth).

## What it drives

`k.contract` puts `401` and `403` on every route this map guards, as [Problem Details](/docs/reference/problem-details-schema), both `no-store`. A public route gets neither:

```ts title="delete-project.ts"
const result = await apiClient.projects.deleteProject({
    params: {
        projectId: 'prj_42',
    },
});

if (result.status === 403) {
    console.log(result.body.detail);
}
```

[`generateOpenApi`](/docs/reference/generate-openapi) emits each route's `security` and the permission it requires:

```yaml title="openapi.yaml"
# generated
paths:
    /projects/{projectId}:
        delete:
            security:
                - member: []
            x-kizuna-requires:
                project: [delete]
```

## Checking on the client

Each client ships `checkAccess`. `@ts-kizuna/fetch` exports it, and the Swift and Kotlin generators emit it.

It takes the caller's role. Put `role` on whatever route tells the interface who is signed in:

```ts title="contract/routes/me.ts"
export const meRoutes = k.routes('me', {
    getMe: {
        method: 'GET',
        path: '/me',
        responses: {
            200: z.object({
                userId: z.string(),
                role: roles.schema,
            }),
        },
    },
});
```

```json title="GET /me"
{
    "userId": "usr_3",
    "role": "admin"
}
```

`roles.schema` is the zod enum of the role names.

The wire carries one word because the contract says what it means:

```
wire     "role": "admin"
roles    admin: { project: ['create', 'read', 'update', 'delete'] }
map      updateProject: { requires: { project: ['update'] } }
answer   admin holds project:update, so allowed
```

A caller with grants beside the role sends those too, and `checkAccess` takes them as the second argument.

A public route is `true` for anyone. A route needing an identity with no `requires` is `true` for any caller of that identity.

Swift and Kotlin answer from the same data:

```swift
let access = checkAccess(role: me.role)

if access.projects.deleteProject {
    showDeleteButton()
}
```

<Callout title="It is the same answer the server gives">
    `checkAccess` reads the map and roles the server reads, so for "may I call this route" it is exact. It knows nothing about one record,
    such as whether this project is in the caller's workspace. That is a `404` from the handler.
</Callout>
